# Планировщик выездов инженеров

Хакатон «Лидеры цифровой трансформации», задача от «Билайн Бизнес»:
интеллектуальный сервис планирования рабочих маршрутов для выездных
инженеров с учётом временных окон и сложности работ.

Сервис распределяет заявки между инженерами и строит порядок объезда,
считает обе обязательные метрики ТЗ и сравнивает их с базовым вариантом,
объясняет, почему заявка у этого инженера и почему другая осталась без
исполнителя, пересчитывает остаток дня на аварию, отказ абонента, выбытие
или задержку инженера, принимает ручное переназначение и статусы от
диспетчера и отвечает, сколько ещё людей нужно, чтобы закрыть то, что не
влезло.

Всё считается на обезличенной выгрузке, выданной организаторами, за
17.08.2026 — три участка, 205 заявок. Контрольную выборку не используем
нигде: её не читает ни один путь исполнения. Для расчёта интернет не
нужен: адреса геокодированы заранее, дорожные матрицы и ломаные по улицам
лежат в репозитории.

**Куда сервис ходит в сеть — полный список.** Подложка карты тянется с
`services.arcgisonline.com`; без сети карта останется серой, но маршруты,
точки и числа на ней рисуются — они свои. Это всё, что происходит, пока
вы смотрите три выданных участка.

Свою выгрузку дня того же формата можно загрузить кнопкой. Вот тут сеть
может понадобиться — и только если в выгрузке есть адреса, которых нет в
выданной. Тогда движок спрашивает координаты у `nominatim.openstreetmap.org`
и, если тот не ответил, у `photon.komoot.io` (около 1,4 с на адрес), а
дороги между новыми точками — у `router.project-osrm.org`. **Эти адреса
при этом уходят на сторонние сервисы**, и мы говорим об этом прямо, чтобы
решение принимали вы. Какой службой найден каждый известный адрес,
записано в `vrptw/data/geocode.json` полем `provider`.

Выключается: `VRPTW_OFFLINE=1` — тогда никаких обращений не будет вовсе,
а про адреса, которых нет в кэше, система честно скажет, что взять их
неоткуда. Маршрутизатор можно указать свой: `VRPTW_OSRM=<адрес>`.

## Запустить

Нужен Python 3.10 или новее. Из корня репозитория.

**На Windows** — двойной щелчок по `поставить.bat`, затем по
`запустить.bat`. Или в консоли:

```
поставить.bat
запустить.bat
```

Команды `python3` в Windows нет: системный псевдоним с таким именем
открывает Microsoft Store и ничего не ставит. Внутри обёрток — `py -3`,
он приходит вместе с Python с python.org.

**На macOS и Linux:**

```bash
python3 -m pip install -r requirements.txt
python3 -m vrptw.server 8000 восток,юго-восток,югоцентр
```

`python3 -m pip`, а не просто `pip`: если на машине несколько Python,
`pip` может поставить пакеты не в тот. Чтобы не трогать системный —
`python3 -m venv .venv`, затем `source .venv/bin/activate` (на Windows
`.venv\Scripts\activate`) и та же команда установки.

Открыть **http://localhost:8000** — там интерфейс диспетчера. Он лежит в
`web/` собранным, поэтому ни node, ни сборки не нужно. Собран командой
`zsh собрать-интерфейс.sh` из `интерфейс/`; **из какой ветки и какого
коммита — в `web/сборка.json`**, и это единственное место, где это
написано: ветка менялась, а проза в README за ней не поспевала.

**Интерфейс лежит здесь дважды, и это нарочно.** В `интерфейс/` —
исходники (vite, TypeScript, React), в `web/` — они же собранными.
Собранное нужно, чтобы движок отдавал страницу сам и проверяющему не
пришлось ставить node; исходники — чтобы было что читать и чем
пересобрать. Пересобрать: `cd интерфейс && npm ci && npx vite build
--outDir ../web`, либо тем же `zsh собрать-интерфейс.sh интерфейс`.

Интерфейс делал второй участник команды. Его рабочий репозиторий
закрыт — в нём остались наши переписка и черновики, — поэтому исходники
лежат здесь копией, снятой с того коммита, которым собран `web/`.
Искать больше нечего: всё, из чего собирается интерфейс, в `интерфейс/`,
и сборка из него воспроизводится (см. `web/сборка.json`).

**Сколько ждать.** Порт открывается сразу. Планы трёх участков на этом
коде лежат готовыми в `vrptw/data/готовые/` — с ними день поднимается за
секунды. Если движок правили, готовые планы перестают подходить (в имени
файла — отпечаток кода), и сервер считает сам: на обычном ноутбуке около
трёх минут. Страница в это время пишет, сколько участков готово, и
открывается сама.

Бюджет поиска задан **в шагах, а не в секундах**: на машине помедленнее
ждать придётся дольше, зато план выйдет тот же самый. Иначе число на
экране зависело бы от того, что ещё крутится на компьютере, и сверить
его с числами ниже было бы нечем.

Все команды — из корня репозитория: сервер пишет своё состояние (архив
расчётов, журнал диспетчера) в текущий каталог.

## Сценарий ТЗ по шагам

| шаг ТЗ | в интерфейсе | то же через API |
|---|---|---|
| 1. Открыть тестовый набор | «Диспетчерская» → «Создать новый расчёт»; свой файл — там же, «День для расчёта» → Excel, CSV или JSON | `/api/plan?day=восток`, `POST /api/uploads` |
| 2. Запустить планирование | «Создать расчёт», переменные движка | `POST /api/runs` |
| 3. Маршруты на карте | вкладка «Обзор» — маршруты по улицам | `routes[].stops[].geometry` |
| 4. Почему этот инженер | точка на карте → «Почему этот исполнитель» | `/api/explain?day=восток` |
| 5. Авария / отмена / выбытие | «Воздействие» → событие по заявке или по инженеру → «Записать» → «Пересчитать остаток дня» | `/api/replan?day=восток&at=820&urgent=2` |
| 6. Что изменилось | окно «Что дал пересчёт» | `meta.replan` |

Сверх сценария: метрики ТЗ и сравнение с базовым — плитки «Исполнителей» и
«Пробег» на пульте (`meta.baseline`); почему заявка без исполнителя — в её
карточке (`unassigned_detail`); ручное закрепление и статусы «отправлено /
в пути / выполнено / сорвано» — в карточке заявки (`POST /api/event`);
«сколько ещё людей нужно» — на «Воздействии» (`/api/staffing`). Все
ручки и поля — в `vrptw/CONTRACT.md` и `frontend_kit/SERVER.md`.

## Как проверить, что всё работает

```bash
python3 -m vrptw.selfcheck        # ~40 с: весь путь движка, 60 отметок
python3 -m vrptw.server check     # около 7 мин: все ручки, 83 отметки
zsh проверка-с-нуля.sh            # клон репозитория с нуля — то, что увидите вы
```

**На Windows команды `python3` нет** — она либо не найдётся, либо откроет
Microsoft Store. Подставляйте `py -3`:

```bash
py -3 -m vrptw.selfcheck
py -3 -m vrptw.server check
py -3 -m vrptw.server 8000 восток,юго-восток,югоцентр
```

Скрипты `проверка-с-нуля.sh` и `собрать-интерфейс.sh` написаны на zsh и
на Windows не запустятся; всё, что они делают, доступно командами выше.


`selfcheck` и `server check` — это и есть набор тестов. Каждый план,
который выходит наружу, проверяется `Plan.check_invariants`: окна, смены,
навык, транспорт и предел перегона, время в пути по дорожной сети на час
выезда, длительность работ и граница суток (22:00). Соврать ему нельзя —
он пересчитывает всё сам.

## Что оптимизируется

Критерии — в порядке, названном заказчиком:

1. **больше выполненных заявок**; внутри — приоритет распределения:
   авария → подключение → ремонт и дозаказ (нераспределённая авария хуже
   99 нераспределённых подключений — веса `PRIORITY_WEIGHTS`, и порядок
   строгий, пока заявок одной ступени в дне меньше ста; на участках их
   56–83);
2. **меньше исполнителей**;
3. **меньше пробег**.

Алгоритм — regret-вставка и поиск большими окрестностями (разрушить и
пересобрать, с отжигом), `vrptw/solvers/`. Две реализации одного
алгоритма — `fast.py` (боевой) и `improved.py` (эталон) — сверяются в
`selfcheck` шаг в шаг. Пошагово — `ФУНКЦИОНАЛЬНЫЕ-ТРЕБОВАНИЯ.md`, раздел 3.

## Числа

Каждое число — с файлом замера и парным 95% интервалом по всем источникам
случайности, если он есть. Файлы — в `замеры-24-09/`.

**Против базового варианта ТЗ**, три участка вместе
(`база-против-нас.txt`, `база-против-нас-интервалы.txt`, 8 зёрен):

| | базовый | наш | разница |
|---|---|---|---|
| назначено из 205 | 81,0 | 191,6 | +110,6 ± 0,4 |
| выполнено (симуляция дня) | 70,7 | 169,3 | +98,6 ± 0,6 |
| исполнителей | 42,0 | 38,8 | −3,2 ± 0,4 |
| км на назначенный визит | 11,74 | 6,60 | −43,8% ± 0,5% |

Пробег валом сравнивать нельзя: мы назначаем в 2,4 раза больше заявок.
По километрам на визит выигрываем на всех трёх участках: Восток
−0,40 ± 0,10, Юго-восток −8,91 ± 0,17, Югоцентр −1,63 ± 0,14.

**Насколько близко к пределу** (`потолок-час.txt`): точная модель на HiGHS
за час. Югоцентр 56 из 56 — оптимум доказан. Восток: наш план в том же режиме
берёт 64 при верхней границе 64,0, HiGHS за час нашёл 63. Юго-восток:
наш 75, HiGHS за час 64, доказанная граница 81 — от нас до предела не
больше шести заявок.

**Пересчёт в течение дня** (`пересчёт-на-зонах.txt`,
`выбытие-на-зонах.txt`, `прокол-на-зонах.txt`): две аварии — +1,78 ± 0,62
визита за 1,51 с, из них 1,89 ± 0,16 аварии из двух, и у 88–90% визитов
исполнитель не меняется; выбытие инженера утром стоит 4,6 визита, пересчёт
возвращает 3,2 ± 1,8; задержка на 40 минут стоит 0,1–0,4 визита, и
пересчёт из неё не возвращает ничего — буферы съедают её сами.

**Сколько ещё людей нужно** (`сколько-людей.txt`): Восток +3, Юго-восток
+5, Югоцентр 0.

**Где ломается день** (`окна-спрос.txt`): окно 10:00–12:00 — на
подключения спрос 28,7 ч работы против 21,0 ч рук.

## Данные и допущения

Выгрузка за 17.08.2026 — `vrptw/data/заявки/`: Восток 66 заявок,
Юго-восток 83, Югоцентр 56; внизу каждого файла — адрес офиса участка,
стартовая точка инженеров. Координат, длительности работ, приоритета,
транспорта и самих инженеров в выгрузке нет; ТЗ разрешает их достроить и
требует назвать допущения:

```bash
python3 -m vrptw.core.load допущения
```

Коротко: длительность — по нормативу организаторов, разложенному по типу
заявки; бригада, транспорт, смены, порядок приоритетов и оборудование на
заявку — наши допущения (синтетику постановщик разрешил прямо, число
исполнителей укладывается в рамку задания). Ни одно
допущение не касается того, как визит прошёл на самом деле: неявку и
разброс длительности симулятор разыгрывает заново в каждом прогоне,
планировщик будущего не видит. Подробно — `ФУНКЦИОНАЛЬНЫЕ-ТРЕБОВАНИЯ.md`,
раздел 5.

## Чего система не делает

* Вероятность неявки и разброс длительности — априорные: истории визитов
  в выгрузке нет.
* Интервала по дням на настоящих данных нет: день один, разложенный на
  три участка. Интервалы выше — по зёрнам солвера и симуляции.
* Оборудование между исполнителями при встрече не передаётся: в машине
  то, что выдали утром.

Полный список — `ФУНКЦИОНАЛЬНЫЕ-ТРЕБОВАНИЯ.md`, раздел 6.
